# `data_preparation.py`

## Назначение

Модуль превращает Excel/CSV-выгрузку иерархической витрины в нормализованную
историю и полную панель `segment_id × cal_date`. Побочных эффектов записи нет.

Это **единственная граница доверия к внешним данным** (boundary layer) и
канонический документ входного контракта. При расхождении с другими страницами
верны этот документ и код `data_preparation.py`.

## Контракт входных данных

### Источник и гранулярность

| Что | Значение |
|---|---|
| YQL | `.proposal/.../qr_yandex_pay/bi/pred_insight.yql`, кластер `hahn` |
| Витрина | `//home/fdt/payoffline/projects/qr_yandex_pay/bi/payoffline_pulse_hier` |
| Вход Python | Excel/CSV-выгрузка витрины, путь в `config.INPUT_PATH` |

Python **не ходит в YT**: он читает файл, полученный выгрузкой витрины. Все
расхождения типов ниже возникают именно на шаге выгрузки.

- **Единица наблюдения:** сегмент за один интервал внутри одного `period`.
- **Ключ строки витрины:** `period × cal_date × slice_depth × geo × products ×
  merchants_type × is_terminal_or_cpqr`.
- **Ключ после фильтра периода:** `segment_id × cal_date`, уникальность обязательна.
- `GROUPING SETS` по 4 измерениям даёт 16 срезов на дату;
  `slice_depth` = число зафиксированных измерений (0 = total, 4 = атом).

Проверено на `payoffline_pulse_hier_28_07.xlsx`: после фильтра `period='1W'` —
2533 строки, 13 недель, 203 сегмента, дубликатов нет.

### Схема полей

| Поле | YQL-тип | Смысл | Единица | NULL | Обработка в Python |
|---|---|---|---|---|---|
| `period` | `String` | `1W`, `4W`, `13W` | — | нет | обязательный фильтр по `config.PERIOD` |
| `cal_date` | `Uint16` | Конец интервала, дни от эпохи | дни | нет | `int`, шаг `7 × N`, где `period = NW` |
| `slice_depth` | `Uint8` | Число зафиксированных измерений | шт | нет | `int`, сверяется с dimensions |
| `geo` | `String?` | География | — | да = агрегат | `str` или `None` |
| `products` | `String?` | Продукт | — | да = агрегат | `str` или `None` |
| `merchants_type` | `String?` | TOP-5 мерчант или `Прочее` | — | да = агрегат | `str` или `None` |
| `is_terminal_or_cpqr` | `String?` | `QR`, `Терминал`, `CPQR` | — | да = агрегат | `str` или `None` |
| `gmv` | `Double` | Оборот captured-платежей | **рубли** | нет | `float`, конечен |
| `tx` | `Uint64` | Captured-транзакции | шт | нет | `float` |
| `au` | `Uint64` | Уникальные пользователи | шт | нет | `float` |
| `am` | `Uint64` | Уникальные мерчанты | шт | нет | `float` |
| `aov` | `Double?` | `gmv / tx` | рубли | да при `tx=0` | `float`, `NaN` сохраняется |
| `tpm` | `Double?` | `tx / am` | шт | да при `am=0` | `float`, `NaN` сохраняется |
| `freq` | `Double?` | `tx / au` | шт | да при `au=0` | `float`, `NaN` сохраняется |
| `share_in_total_gmv` | `Double?` | Доля в total GMV | доля | да | не используется, доля считается заново |
| `authzone_tx_numerator` | `Uint64` | Captured authzone-транзакции | шт | нет | `float`, конечен, неотрицателен |
| `authzone_tx_share` | `Double?` | `authzone_tx_numerator / tx` | доля | да при `tx=0` | авторитетное YQL-значение; Python не пересчитывает |

YQL дополнительно пишет относительные метрики и их сырые числители. Python
активирует восемь локальных отношений из реестра `RATIO_METRICS`. Старая
GMV-выгрузка без специализированных колонок по-прежнему обрабатывается, а
недоступные относительные метрики помечаются как пропущенные.

### Фактические типы: почему всё приходит как `object`

**Первая строка выгрузки — служебный заголовок типов YT**, а не данные:
`period='string'`, `cal_date='uint16'`, `gmv='double'`, … Именно поэтому в
`load_history_table` стоит фильтр `df["period"].astype(str) != "string"`: он
отбрасывает строку типов **до** приведения типов, иначе `astype(int)` упал бы
на значении `'uint16'`. Значение `'string'` в колонке `period` — единственный
маркер этой строки.

**Числовые значения могут приезжать строками.** Замер на
`payoffline_pulse_hier_28_07.xlsx` (все 15 колонок имеют dtype `object`):

| Поле | `str` | `float` | `int` |
|---|---:|---:|---:|
| `gmv` | 2792 | 1705 | 1102 |
| `aov` | 4874 | 546 | 179 |
| `freq` | 2892 | 335 | 2372 |

Пример строкового `gmv`: `'2.7927989186000025e+08'`. Строковые числа —
**штатный вариант входа**, а не порча данных: защитные преобразования в
`load_history_table` удалять нельзя.

### NULL, NaN и `Unknown` — три разные сущности

| Ситуация | В YQL | В Python | Смысл |
|---|---|---|---|
| Измерение свёрнуто в срезе | `IF(GROUPING(...)==1, NULL, ...)` | `None` | **Агрегированный уровень** |
| Значения нет в источнике | `COALESCE(..., 'Unknown')` | `'Unknown'` | **Реальное неизвестное значение** |
| Отношение не определено | `NULL` при нулевом знаменателе | `NaN` | «Неприменимо», **не ноль** |
| Строки сегмента нет за неделю | строки нет | `gmv=0`, `row_missing_in_source=True` | Нет оборота |

Замена `NULL → 'Unknown'` идёт **до** `GROUPING SETS`, поэтому агрегированный
уровень (приходит как `NaN`) и реальное неизвестное значение (непустая строка)
никогда не смешиваются.

⚠️ Рост сегмента `geo=Unknown` может означать не бизнес-аномалию, а ухудшение
заполненности источника.

### Временные окна

| Правило | Значение | Где обеспечено |
|---|---|---|
| Глубина истории | 13 интервалов | `$history_periods` в YQL |
| Минимум для расчёта | 4 интервала в total-слое | `load_history_table` |
| Шаг календаря | ровно `7 × N` дней, где `period = NW` | `load_history_table` |
| Текущая неделя | последняя либо `config.CURRENT_CAL_DATE` | `build_anomaly_candidates` |
| WoW-переходов | `13 − 1 = 12`: 11 исторических + текущий | `calculate_segment_anomaly` |
| TOP-5 мерчантов | предыдущие 12 интервалов, **без текущего** | `cal_date_index >= 1 AND <= 12` |

**Последняя неделя считается полностью закрытой** — это осознанное проектное
решение, а не упущение. Гарантия в YQL: интервал попадает в витрину, только
если обе его границы покрыты данными источника
(`cal_date - (period_days - 1) >= min_source_date AND cal_date <= max_source_date`).
Неполный интервал в витрину не попадает, поэтому исключать его в Python
**не нужно**.

⚠️ Состав TOP-5 пересчитывается на каждом запуске и **меняется между
запусками**: мерчант может быть отдельной категорией в `1W` и попасть
в `Прочее` в `4W`/`13W`. Историческая сопоставимость категорий не гарантируется.

### Гарантии после boundary layer

Внутренний код вправе на них полагаться и не обязан повторять проверки типов:

1. Ровно один `period`, совпадающий с обязательным параметром запуска.
2. `cal_date`, `slice_depth` — `int`; `gmv`, `tx`, `au`, `am` — конечные `float`.
3. Dimension values — `str` без крайних пробелов либо `None`.
4. `segment_id × cal_date` уникален.
5. `slice_depth` согласован с числом заполненных dimensions.
6. Metadata одного `segment_id` одинакова на всех неделях.
7. Календарь total-слоя полон, `total_gmv > 0` на каждой неделе.
8. Все даты сегментов принадлежат календарю total-слоя.
9. `aov`, `tpm`, `freq` могут быть `NaN` — допустимое состояние.
10. Каждая доступная относительная метрика сверена со своим аддитивным
    числителем и знаменателем; при нулевом знаменателе числитель равен нулю,
    а значение метрики равно `NULL`.

После `build_full_week_grid` дополнительно: панель содержит ровно
`сегменты × недели` строк; отсутствовавшая строка имеет `gmv=0`, `tx/au/am=0`,
`row_missing_in_source=True`, ratio-метрики остаются `NaN`.

## `load_history_table`

Поддерживает `.xlsx`, `.xls`, `.csv`.

Обязательные колонки: `period`, `cal_date`, `slice_depth`, `gmv`, `tx`, `au`, `am`.

Последовательность:

1. Читает файл.
2. Требует колонку и обязательный аргумент `period` формата `<N>W`, удаляет
   служебную строку `period == "string"`, применяет фильтр и требует непустой
   вход с ровно одним периодом.
3. Приводит `cal_date/slice_depth/gmv/tx/au/am` к числам; пустое, нечисловое или
   бесконечное значение немедленно отклоняет с диагностикой строк.
4. Приводит доступные `aov/tpm/freq` к числам, разрешая штатный NULL.
5. Для каждой активированной спецификации строго валидирует контракт отношения.
6. Определяет dimensions и нормализует их значения.
6. Добавляет JSON `segment_id`, человекочитаемые `segment_key`, `segment_level`.
7. Сверяет вычисленную глубину сегмента с входным `slice_depth`, валидирует
   `segment_key` и согласованность metadata сегмента между неделями.
8. Проверяет уникальность `segment_id × cal_date`.
9. По `slice_depth=0` строит список недель, проверяет календарь и отклоняет
   любую сегментную дату, отсутствующую в total-календаре.

Dimensions зафиксированы в `config.DIM_COLUMNS`. Любая другая колонка входного Excel
считается технической, входит в `ANOMALY_TECH_COLUMNS` в рамках конкретной
выгрузки и не участвует в `segment_id`, `segment_key` или coverage.

Любое нарушение вызывает `ValueError` с примерами проблемных строк. Строки
**не удаляются молча**.

Жёсткие проверки:

- выбран ровно один непустой `period`, совпадающий с обязательным аргументом;
- обязательные числовые поля заполнены, числовые и конечные;
- total-слой существует;
- все даты входных строк входят в total-календарь;
- ключ `segment_id × cal_date` уникален;
- входной `slice_depth` равен числу заполненных dimensions; `segment_key` и
  `segment_level` согласованы с ними;
- metadata (`slice_depth`, ключ, уровень и dimensions) одинакова во всех
  неделях одного `segment_id`;
- есть минимум четыре недели;
- шаг между соседними `cal_date` равен `7 × N`, где выбранный `period = NW`;
- total GMV строго положителен.

`dates` строится по агрегированному total-слою, поэтому именно total определяет
временную ось всего дальнейшего анализа.

## Идентификаторы сегмента

Для dimensions `["geo", "products"]`:

| Значения | `segment_id` | `segment_key` | `segment_level` |
|---|---|---|---|
| `None`, `None` | `[null,null]` | `ИТОГО` | `ИТОГО` |
| `РФ`, `None` | `["РФ",null]` | `geo=РФ` | `geo` |
| `РФ`, `QR` | `["РФ","QR"]` | `geo=РФ × products=QR` | `geo × products` |

JSON сохраняет фиксированный порядок dimensions и однозначно отличает реальную
строку `"∅"` от пропуска `null`, а также безопасно кодирует `|`, `=` и Unicode.

`segment_id` — именно JSON-массив, **не** строка со значениями через `|`.

### Разбор `segment_key`

Единственная функция разбора — `segment_keys.parse_segment_key_parts`; её
используют `data_preparation`, `set_packing` и `reporting`. Раньше в пакете
жили две независимые копии парсера с разным поведением: одна молча пропускала
неразбираемую часть, вторая выбрасывала исключение.

- Разделитель ровно один — ` × ` (U+00D7), тот же, которым ключ и собирается.
  Латинская `x` разделителем больше не считается: она ломала значения вида
  `A x B`.
- Неразбираемая часть ключа — ошибка контракта: `ValueError`, а не пропуск.
  Молчаливый пропуск занижал бы глубину сегмента и портил coverage.
- Значение с `=` внутри разбирается корректно: режем по первому `=`.

⚠️ Ограничение: значение измерения не должно содержать подстроку ` × `.

Вычисленная глубина ключа строго сверяется с входным `slice_depth` на этапе
`load_history_table`. Вход отклоняется до расчёта аномалий, если, например,
`geo=РФ × products=QR` имеет `slice_depth = 1`, либо metadata одного
`segment_id` различается между неделями.

## `build_full_week_grid`

1. Берёт одну metadata-строку на `segment_id`.
2. Переносит предагрегированные YQL значения без повторной агрегации.
3. Строит декартову сетку всех сегментов и всех total-недель.
4. Для действительно отсутствующей строки заполняет `gmv/tx/au/am` и сырые числители нулями.
5. Сохраняет NULL относительных метрик: отношение при нулевом знаменателе или у
   восстановленной строки остаётся неопределённым.
6. Добавляет `row_missing_in_source` по результату соединения с исходными строками.

## Критичные семантические решения

- Отсутствующая строка источника становится нулём по аддитивным показателям для
  статистики и отмечается `row_missing_in_source`. Повреждённая существующая
  строка не может попасть в этот сценарий: она отклоняется при загрузке.
- Нормализация бизнес-категорий остаётся ответственностью upstream YQL. Python
  не склеивает регистр, Unicode-варианты или специальные категории.
- По подтверждённому upstream-контракту отрицательные GMV и счётчики невозможны;
  отдельная проверка знака в Python не выполняется.
- `pred_insight.yql` формирует одну строку на `period × cal_date × segment_id`.
  После фильтрации выбранного `period` ключ `segment_id × cal_date` обязан быть
  уникальным. Дубликаты считаются нарушением входного контракта и отклоняются
  в `load_history_table`; Python не исправляет их повторной агрегацией.
- Новая колонка Excel не меняет состав dimensions: она считается технической и
  не становится частью `segment_id`. Для изменения сегментации нужно явно
  изменить `DIM_COLUMNS` и синхронно обновить входной контракт и тесты coverage.
- Перед `drop_duplicates` проверяется согласованность metadata одного
  `segment_id`, поэтому `build_full_week_grid` не может молча выбрать первую
  из противоречивых строк.
