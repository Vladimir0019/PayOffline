# `pred_insight.yql`: документация

## Краткое назначение

Скрипт строит и полностью перезаписывает иерархическую витрину метрик QR Yandex Pay:

- источник: `//home/fdt/payoffline/projects/qr_yandex_pay/bi/payoffline_pulse_raw`;
- результат: `//home/fdt/payoffline/projects/qr_yandex_pay/bi/payoffline_pulse_hier`;
- поддерживаемые окна: `1W` (7 дней), `4W` (28 дней), `13W` (91 день);
- глубина истории: не более 13 интервалов каждого типа;
- измерения: `geo`, `products`, `merchants_type`, `is_terminal_or_cpqr`;
- базовые метрики: `gmv`, `tx`, `au`, `am`, `aov`, `tpm`, `freq`;
- долевые метрики: `share_in_total_gmv`, `success_rate`, `refund_tx_share`,
  `authzone_tx_share`, `payapp_tx_share`, `split_gmv_share`,
  `credlim_gmv_share`, `tips_gmv_share`, `cashback_gmv_share`.

Витрина является прямым входом для `Insight_base.yql`, то есть от корректности
этого скрипта зависит поиск и интерпретация аномалий.

> [!note]
> Документ составлен по актуальному коду `pred_insight.yql` и подтверждённым
> владельцем условиям источника. Схемы и данные YT в этой сессии не читались.

## Подтверждённый контракт входных данных

Следующие условия считаются гарантированными upstream-контрактом и не являются
рисками данного скрипта:

1. Источник не содержит буквальные значения `Unknown` и `Прочее`.
2. Сценарий записи пустого результата невозможен: входные данные корректны и
   содержат необходимые строки.
3. Ключ `(checkout_order_id, period)` практически уникален. Доля строк с
   уникальным ключом составляет `0.9999987244655949`; редкие дубли признаны
   несущественными и не требуют `COUNT(DISTINCT checkout_order_id)`.
4. `cal_date_index` не бывает отрицательным.
5. `amount` не бывает отрицательным.
6. Последовательность `cal_date` непрерывна.
7. Витрина используется контуром поиска аномалий.

Важно: сам YQL не валидирует большинство этих условий, а доверяет источнику.
При изменении upstream-процесса контракт должен быть перепроверен.

## Уникальность `(checkout_order_id, period)`

Практический ключ строки на уровне заказа:

```text
checkout_order_id + period
```

Измеренное качество ключа:

| Показатель | Значение |
|---|---:|
| Доля строк с уникальным `(checkout_order_id, period)` | `0.9999987244655949` |
| То же в процентах | `99.99987244655949%` |
| Доля строк, относящихся к неуникальным ключам | `0.0000012755344051` |
| То же в процентах | `0.00012755344051%` |
| Эквивалент на 1 млн строк | примерно `1.2755` строки |

Абсолютной уникальности нет, но отклонение составляет приблизительно
`1.28 ppm`. Для текущего расчёта оно признано пренебрежимо малым:

- предварительная дедупликация не выполняется;
- `tx0` и `tx` считаются через обычный `COUNT(checkout_order_id)`;
- редкие дубли могут дать минимальное завышение счётчиков и связанных метрик,
  но это принято как допустимая погрешность;
- величина фактического влияния на конкретный срез зависит от `status`,
  измерений и `amount` дублирующихся строк, поэтому её нельзя считать строго
  равной общей доле дублей.

Это осознанное аналитическое допущение, а не гарантия строгой уникальности.
Если показатель уникальности заметно ухудшится относительно
`0.9999987244655949`, решение об игнорировании дублей нужно пересмотреть.

## Гранулярность результата

Одна строка соответствует комбинации:

```text
period
× cal_date
× конкретный набор включённых измерений
× значения включённых измерений
```

`cal_date` — дата конца окна. Не включённые в конкретный срез измерения
записываются как `NULL`.

Примеры:

- `slice_depth = 0` — total по `period + cal_date`, все измерения равны `NULL`;
- `slice_depth = 1` — срез по одному измерению;
- `slice_depth = 4` — атомарный срез по всем четырём измерениям.

Скрипт формирует все 16 вариантов набора измерений:

```text
C(4,0) + C(4,1) + C(4,2) + C(4,3) + C(4,4)
= 1 + 4 + 6 + 4 + 1
= 16 GROUPING SETS
```

Это не 16 строк на дату: каждый grouping set порождает строки по всем
встреченным комбинациям значений.

| Кешбэк | `cashback_amount` |

## Логика выполнения

### 1. Конфигурация периодов

| Переменная | Значение | Смысл |
|---|---:|---|
| `$history_periods` | `13` | В витрину попадают индексы `< 13` |
| `$top_merchants_history_periods` | `12` | TOP-5 использует индексы 1–12 |

Справочник `$periods` задаёт:

| `period` | `period_days` |
|---|---:|
| `1W` | 7 |
| `4W` | 28 |
| `13W` | 91 |

Другие значения `period` отбрасываются через `INNER JOIN`.

### 2. Границы источника

`$source_bounds` отдельно для каждого поддерживаемого `period` вычисляет:

- `min_source_date = MIN(CAST(created_at AS Date))`;
- `max_source_date = MAX(CAST(created_at AS Date))`.

### 3. Отбор истории

`$source_complete_periods` оставляет:

- не более 13 интервалов: `cal_date_index < 13`;
- окна, левая граница которых не раньше `min_source_date`;
- окна, дата окончания которых не позже `max_source_date`.

Поскольку по контракту `cal_date_index >= 0`, фактический диапазон индексов —
от 0 до 12.

По контракту `cal_date` непрерывен. Для downstream-поиска аномалий ожидаемый
шаг между соседними датами равен 7, 28 или 91 дню в зависимости от `period`.

### 4. TOP-5 типов мерчантов

TOP-5 рассчитывается независимо для `1W`, `4W` и `13W`:

1. используются только строки `status = 'captured'`;
2. текущий интервал `cal_date_index = 0` исключается;
3. берутся доступные индексы 1–12;
4. по каждому `merchants_type` считается `SUM(ABS(amount))`;
5. сортировка: оборот по убыванию, затем имя типа по возрастанию;
6. `ROW_NUMBER <= 5` оставляет ровно пять категорий, если доступно не менее пяти.

TOP-5 относится к типам/брендам мерчантов, а не к отдельным `merchant_id`.

Так как `amount` неотрицателен, `ABS(amount)` не меняет результат и является
избыточной, но безопасной защитной обёрткой.

### 5. Нормализация измерений

В `$source_history`:

- исходный `NULL` в `geo`, `products`, `is_terminal_or_cpqr` заменяется на
  техническое значение `Unknown`;
- `NULL` в `merchants_type` становится `Unknown`;
- тип мерчанта из TOP-5 сохраняет исходное значение;
- остальные ненулевые типы объединяются в `Прочее`;
- `user_cohort` переименовывается в `users_activity`;
- `users_newness` и `users_activity` далее не агрегируются и не попадают в
  output.

Источник не может содержать буквальные `Unknown` и `Прочее`, поэтому
технические категории однозначны и не смешиваются с реальными значениями.

### 6. Классификация authzone

Вычисляемый признак `is_authzone` равен 1, если:

- `credlim_flg = true`; либо
- `payment_method` не равен `UNIQR_ONETIME`/`UNIQR_REUSABLE` и не является
  `NULL`.

Признак равен 0 для:

- `UNIQR_ONETIME`;
- `UNIQR_REUSABLE`;
- `payment_method IS NULL`, если одновременно не установлен `credlim_flg`.

Порядок `CASE` важен: `credlim_flg` имеет приоритет над `payment_method`.

### 7. Агрегация

Для каждой пары `period + cal_date` и каждого из 16 grouping sets считаются
базовые метрики и числители платёжных рычагов.

#### Базовые агрегаты

| Поле | Формула | Смысл |
|---|---|---|
| `gmv` | сумма `amount / 100.0` для `captured` | Успешный GMV в основных денежных единицах |
| `tx0` | `COUNT(checkout_order_id)` по всем статусам | Все практически уникальные заказы/попытки, знаменатель success rate |
| `tx` | `COUNT(checkout_order_id)` для `captured` | Практически уникальные успешные заказы |
| `au` | `COUNT(DISTINCT phone_token)` для `captured` | Активные пользователи |
| `am` | `COUNT(DISTINCT merchant_id)` для `captured` | Активные мерчанты |

Ключ `(checkout_order_id, period)` практически, но не абсолютно уникален.
Обычный `COUNT` может минимально завышать `tx0` и `tx`; при текущей доле
уникальных строк `0.9999987244655949` эффект принят как несущественный.

#### Числители транзакционных долей

| Поле | Условие |
|---|---|
| `refund_tx_numerator` | captured-заказ и `refunds_cnt_payment_id > 0` |
| `authzone_tx_numerator` | captured-заказ и `is_authzone = 1` |
| `payapp_tx_numerator` | captured authzone-заказ, есть `appmetrika3_qr_qrc_id`, а `start_user_agent_media` или `start_media` равен `ios`/`android` |

`refund_tx_numerator` считает число заказов с признаком наличия возврата, а не
сумму `refunds_cnt_payment_id`.

#### Числители GMV-долей

| Поле | Формула |
|---|---|
| `split_gmv_numerator` | GMV captured-платежей с `payment_method IN ('SPLIT', 'SPLIT_SBP')` |
| `credlim_gmv_numerator` | GMV captured-платежей с `credlim_flg = true` |
| `tips_gmv_numerator` | сумма `tips_recive_amount_sum / 100.0` для captured-строк с `tips_show_staff_cnt > 0` |
| `cashback_gmv_numerator` | сумма положительного `cashback_amount / 100.0` для captured-строк |

### 8. Производные метрики

#### Базовые метрики

| Метрика | Формула | Нулевой знаменатель |
|---|---|---|
| `aov` | `gmv / tx` | `NULL` |
| `tpm` | `tx / am` | `NULL` |
| `freq` | `tx / au` | `NULL` |
| `share_in_total_gmv` | GMV сегмента / total GMV даты | `NULL` |

#### Конверсия и платёжные рычаги

| Метрика | Формула | Нулевой знаменатель |
|---|---|---|
| `success_rate` | `tx / tx0` | `NULL` |
| `refund_tx_share` | `refund_tx_numerator / tx` | `NULL` |
| `authzone_tx_share` | `authzone_tx_numerator / tx` | `NULL` |
| `payapp_tx_share` | `payapp_tx_numerator / tx` | `NULL` |
| `split_gmv_share` | `split_gmv_numerator / gmv` | `NULL` |
| `credlim_gmv_share` | `credlim_gmv_numerator / gmv` | `NULL` |
| `tips_gmv_share` | `tips_gmv_numerator / gmv` | `NULL` |
| `cashback_gmv_share` | `cashback_gmv_numerator / gmv` | `NULL` |

Метрики конверсии и платёжных рычагов используют единую семантику: при
знаменателе, равном или меньшем нуля, метрика не определена и возвращает
`NULL`. Нулевой числитель при положительном знаменателе по-прежнему даёт
наблюдаемое значение `0.0`. Это позволяет отличить отсутствие базы для расчёта
от фактической нулевой конверсии или доли.

### 9. Запись

`INSERT INTO $output_table WITH TRUNCATE` полностью заменяет содержимое
`payoffline_pulse_hier`.

В output передаются не только готовые доли, но и их аддитивные компоненты:
`tx0`, `refund_tx_numerator`, `authzone_tx_numerator`, `payapp_tx_numerator`,
`split_gmv_numerator`, `credlim_gmv_numerator`, `tips_gmv_numerator`,
`cashback_gmv_numerator`. Знаменатели `tx` и `gmv` уже входят в output.

По подтверждённому контракту вход всегда корректен, поэтому пустой insert не
рассматривается как возможный рабочий сценарий.

`ORDER BY` отсутствует. Порядок строк не входит в контракт витрины; потребители
обязаны задавать сортировку самостоятельно.

## Семантика специальных значений

| Значение | Смысл |
|---|---|
| `NULL` в выходном измерении | Измерение не входит в данный grouping set |
| `NULL` в производной метрике | У метрики отсутствует положительный знаменатель; значение не определено |
| `Unknown` | В исходной строке измерение было `NULL` |
| `Прочее` | Ненулевой `merchants_type` не вошёл в TOP-5 периода |

Коллизий с реальными значениями нет: источник не содержит `Unknown` и
`Прочее`.

## Зависимость поиска аномалий

Текущий локальный pipeline `gmv_anomaly` читает Excel/CSV-выгрузку этой витрины. Пилотный
контур `authzone_tx_share` использует готовую YQL-долю, `authzone_tx_numerator` и `tx`.
Python не пересчитывает готовую долю, а сверяет её с компонентами на boundary layer.
`Insight_base.yql` в область данного изменения не входит.

Критичные для anomaly-контракта свойства:

1. Непрерывность `cal_date` с шагом 7/28/91 день.
2. Ровно одна total-строка `slice_depth = 0` на `period + cal_date`.
3. Каждая дата сегментной строки входит в total-календарь своего периода.
4. `period`, `cal_date`, `slice_depth`, `gmv`, `tx`, `au`, `am` обязательны;
   числовые поля заполнены и конечны.
5. `aov`, `tpm`, `freq` могут быть `NULL` при нулевом знаменателе.
6. Стабильные имена и типы базовых колонок.
7. `NULL` у измерения означает, что оно не входит в grouping set.
8. Единая классификация TOP-5 внутри одного запуска.
9. Отсутствие зависимости от физического порядка строк.

Downstream Python строго применяет переданный `period` и требует после фильтра
ровно одно значение. Его технический `segment_id` — компактный JSON-массив
четырёх dimension values в фиксированном порядке; JSON `null` однозначно
отличается от буквальной строки `"∅"`. Человекочитаемый ключ хранится отдельно.

При построении полной панели действительно отсутствующая строка получает нули
по `gmv/tx/au/am`; `aov/tpm/freq` остаются неопределёнными. Повреждённая
существующая строка с пустым, нечисловым или бесконечным обязательным значением
отклоняется и не может быть восстановлена как искусственный ноль.

Нормализация бизнес-категорий является ответственностью данного upstream-контура:
Python не выполняет case-folding, Unicode-нормализацию и смысловую склейку
категорий. Неотрицательность `amount` и производных GMV/счётчиков остаётся
подтверждённым upstream-инвариантом.

Изменение этих свойств требует совместного регрессионного теста
`pred_insight.yql` и `Insight_base.yql`.

## Неочевидные свойства и ограничения

### TOP-5 меняется между запусками

TOP-5 пересчитывается отдельно для каждого периода. Один `merchants_type`
может быть отдельной категорией в `1W`, но попасть в `Прочее` в `4W`/`13W`.

### История переклассифицируется актуальным TOP-5

Список TOP-5 определяется один раз по индексам 1–12 относительно текущего
интервала и применяется ко всем `cal_date` выгружаемой истории данного
`period`.

Исторический сегмент может сменить категорию между запусками без изменения
исходных транзакций. Внутри одного запуска классификация едина, что необходимо
для сопоставимости временного ряда поиска аномалий.

### Периоды перекрываются

`1W`, `4W`, `13W` — альтернативные окна одних данных, а не независимые части.
Их GMV нельзя складывать.

### Доли сегментов суммируются только внутри одного grouping set

`share_in_total_gmv` использует один total для всех 16 grouping sets. Сумма
долей близка к 1 только внутри конкретного набора измерений.

Суммирование долей разных `slice_depth` или разных grouping sets создаёт
многократный счёт.

### Платёжные рычаги не являются взаимоисключающими

- Pay App является подмножеством authzone по формуле скрипта.
- Split и credit limit могут пересекаться, если это допускают входные признаки.
- Чаевые и кешбэк являются денежными отношениями к GMV, а не долями заказов.

Поэтому сумму `authzone_tx_share + payapp_tx_share` или сумму всех GMV-share
нельзя интерпретировать как 100%.

### Новые payment methods по умолчанию считаются authzone

Любой ненулевой `payment_method`, кроме `UNIQR_ONETIME` и `UNIQR_REUSABLE`,
попадает в `is_authzone = 1`. При появлении нового метода оплаты классификацию
нужно отдельно проверить.

### Неиспользуемые поля

`users_newness` и `users_activity` проходят через промежуточный слой, но не
входят в grouping sets и output. Они не влияют на витрину и поиск аномалий.

## Оставшиеся технические замечания

### Денежная точность

GMV и часть числителей делятся на `100.0` внутри `SUM`, то есть агрегируются как
`Double`. Возможны минимальные floating-point-расхождения. Более точный паттерн:

```text
SUM(amount_in_minor_units) / 100.0
```


## Регрессионные проверки

Проверки предназначены не для оспаривания подтверждённых входных инвариантов,
а для защиты контракта при будущих изменениях.

1. Для каждого `period + cal_date` существует ровно одна строка
   `slice_depth = 0`.
2. Ключ
   `period + cal_date + geo + products + merchants_type + is_terminal_or_cpqr`
   с учётом `NULL` уникален.
3. `slice_depth` равен числу непустых измерений.
4. Шаг `cal_date` равен 7/28/91 дню для `1W`/`4W`/`13W`.
5. Для каждого grouping set сумма GMV равна total GMV.

## Правила безопасного изменения

До изменения бизнес-логики необходимо отдельно согласовывать:

- число и метод расчёта TOP-категорий;
- формулу `is_authzone`;
- признаки Pay App;
- определения refund, Split, credit limit, tips и cashback;
- семантику нулевого знаменателя;
- состав измерений и `GROUPING SETS`;
- имена и типы колонок, используемых `Insight_base.yql`.

После любого такого изменения нужно совместно проверить построение витрины и
поиск аномалий.
