# Заметки по аномалиям

Файл содержит отложенные решения, идеи для последующих итераций и вопросы,
которые не должны потеряться при первой реализации долевых метрик.

## Зафиксированная область текущей задачи

- Основной расчёт GMV сохраняется без изменения бизнес-логики.
- Добавляются восемь долевых метрик: `success_rate`, `refund_tx_share`,
  `authzone_tx_share`, `payapp_tx_share`, `split_gmv_share`,
  `credlim_gmv_share`, `tips_gmv_share`, `cashback_gmv_share`.
- Каждая метрика получает собственные кандидаты, score и независимый вызов
  Set Packing. Между метриками нет общего objective и взаимного исключения.
- `Insight_base.yql` не входит в область текущей задачи.
- В существующий Excel добавляется отдельный long-лист долевых метрик с
  колонкой `metric_name`. GMV в этот лист не попадает; существующие листы GMV
  сохраняют прежнюю семантику.
- `metric_value` считается в YQL и является авторитетным значением. Python не
  пересчитывает его для существующих строк. `metric_numerator` и
  `metric_denominator` передаются для materiality, диагностики и обработки
  пропущенных строк.
- Для долей robust z-score на первой итерации считается по абсолютному
  изменению доли, а не по относительному WoW.

## Reliability Factor — вернуться после первой итерации

На первой итерации для всех метрик используется действующее GMV-правило:
reliability зависит от числа ненулевых исторических недель GMV.

Нужно проверить на реальных результатах альтернативы:

1. Число исторических переходов, в которых доля определена с обеих сторон.
2. Минимальный размер знаменателя в текущем и предыдущем периодах.
3. Комбинированный коэффициент:
   `gmv_history_reliability × metric_denominator_reliability`.
4. Для transaction-share использовать `tx0`/`tx`, для GMV-share — `gmv`.

Причина пересмотра: большой GMV не гарантирует достаточное число транзакций,
а нулевая доля является валидным наблюдением и не должна считаться отсутствием
истории.

## Materiality долевой метрики — выбрать после пилота

### Вариант 1. Изменение числителя

```text
impact = numerator_current - numerator_previous
```

Плюсы: простота, аддитивность по иерархии, полная аналогия с GMV.
Минус: не обнаруживает изменение доли, вызванное только знаменателем.

### Вариант 2. Прямой rate-effect сегмента

```text
rate_delta = rate_current - rate_previous
direct_rate_effect = rate_delta × denominator_current
```

Эквивалентная интерпретация:

```text
direct_rate_effect =
    numerator_current - rate_previous × denominator_current
```

Это отклонение текущего числителя от значения, которое получилось бы при
сохранении прошлой доли на текущем объёме знаменателя.

Плюс: учитывает и долю, и размер базы. Минус: direct rate-effect родителя не
обязан равняться сумме direct rate-effect его детей, поэтому materiality и
hierarchy capture могут потерять аддитивность.

### Вариант 3. Атомарный rate-effect — предпочтительный для проверки

Для каждого атома:

```text
atomic_rate_effect =
    (atomic_rate_current - atomic_rate_previous)
    × atomic_denominator_current
```

Для произвольного сегмента:

```text
segment_rate_effect =
    Σ atomic_rate_effect по coverage сегмента

gross_atomic_rate_effect =
    Σ abs(atomic_rate_effect) по всем атомам

materiality_share =
    abs(segment_rate_effect) / gross_atomic_rate_effect
```

Плюсы: знаменатель учтён, эффект аддитивен по coverage, materiality находится
в диапазоне `[0, 1]`, dominance capture считается последовательно.

Ограничение: показатель отражает изменение долей внутри атомов и может не
полностью отражать mix-effect агрегированного родителя. В диагностике стоит
сохранять:

```text
direct_rate_effect
atomic_rate_effect_sum
mix_effect = direct_rate_effect - atomic_rate_effect_sum
```

На пилотной метрике полезно одновременно сохранить варианты 2 и 3 в
диагностике и сравнить их распределения, долю parent materiality выше 1 у
прямого эффекта и состав итоговых аномалий.

Отдельно проверить атомы, у которых доля не определена в одной из двух недель.
Нельзя молча считать их изменение доли нулевым. Возможные решения: исключать
их из observable gross movement с отдельной долей покрытия; исключать
кандидата при слишком низком observable coverage; либо использовать прямой
rate-effect самого кандидата. Выбор нужно сделать по результатам пилота.

## Статистическая модель долей — возможное развитие

### Logit-преобразование

Для доли `p`:

```text
logit(p) = ln(p / (1 - p))
```

Оно переводит долю из диапазона `(0, 1)` на всю числовую ось и лучше различает
изменения около 0 и 1. Нужна регуляризация для `p = 0` и `p = 1`, например
псевдосчётчики.

### Variance stabilization

Для долей по транзакциям статистический шум зависит от знаменателя:

```text
standard_error ≈ sqrt(p × (1 - p) / n)
```

Изменение `1 п.п.` при `n = 100` и при `n = 1 000 000` имеет разную
статистическую значимость. В будущем можно рассмотреть logit, arcsin-sqrt,
Wilson/binomial residual или beta-binomial модель. Для `tips_gmv_share` и
`cashback_gmv_share` биномиальная модель напрямую неприменима.

## Неопределённые и невалидные значения

Нужно сохранять в диагностике и не допускать в solver:

- `NULL`, `NaN`, пустую строку и нечисловое значение `metric_value`;
- `+inf` и `-inf`;
- долю с неположительным знаменателем;
- нарушение допустимого диапазона метрики;
- отсутствующую строку сегмента, восстановленную сеткой.

Отдельно различать ожидаемый `NULL` из-за нулевого знаменателя и повреждённое
значение существующей строки. Возможные статусы:

- `METRIC_UNDEFINED_ZERO_DENOMINATOR`;
- `METRIC_ROW_MISSING_IN_SOURCE`;
- `INVALID_METRIC_VALUE`;
- `INVALID_NUMERATOR`;
- `INVALID_DENOMINATOR`.

Переходы `NULL → value` и `value → NULL` пока не получают lifecycle z-score.
Вернуться к этому после анализа диагностических строк.

## Пороговая калибровка

После пилота подобрать отдельно для каждой метрики:

- `sigma_floor`;
- `min_z_score`;
- `min_materiality_share`;
- минимальный абсолютный rate-effect;
- минимальный знаменатель, если такой фильтр будет добавлен;
- пороги dominance capture и hierarchy bonus, если распределение score
  существенно отличается от GMV.

Особенно проверить редкие `refund_tx_share`/`payapp_tx_share` и метрики,
которые могут быть больше единицы (`tips_gmv_share`, `cashback_gmv_share`).

## `share_in_total_gmv`

Рассмотреть после пилота основной долевой метрики. Эта доля проще остальных:
внутри одной даты знаменатель общий, а изменение доли аддитивно по атомам.
Для неё можно использовать:

```text
metric_value = share_in_total_gmv
metric_numerator = gmv
metric_denominator = total_gmv
```

Перед включением проверить, не дублирует ли её результат GMV-анализ и не
создаёт ли она избыточный менеджерский сигнал.

## Граф долевых аномалий

Существующую раскладку DAG можно переиспользовать. Требуется параметризовать:

- источник данных и фильтр `metric_name`;
- колонку направления вместо `Delta GMV`;
- формат подписи: процентные пункты и rate-effect вместо рублей;
- имя выходного файла.

Предпочтительный результат — отдельный PNG/SVG/PDF для каждой долевой метрики.
Нужно отдельно решить, строить граф по всем eligible-кандидатам или только по
метрикам, где Set Packing выбрал хотя бы одну аномалию.

## Проверки после расширения

- Отдельная оптимизация действительно вызывается один раз на метрику.
- Результат одной метрики не зависит от eligible/score другой метрики.
- Невалидная доля остаётся в диагностике и не попадает в solver.
- Нулевая валидная доля не превращается в `NULL`.
- Отсутствующая строка не создаёт ложное изменение доли `-100%`.
- Materiality и dominance capture согласованы с выбранным определением
  rate-effect.
- GMV-листы и существующий GMV-граф не меняют контракт.
- Новый long-лист не содержит `metric_name = 'gmv'`.
- Граф одной долевой метрики не смешивает узлы других метрик.
